# 스탯 산출 규칙

> 2026-08-24. 축·스킬 매핑은 `tools/build_stats.py`의 `AXES`, 이 문서는 환산 규칙만.

## 규칙

1. **방향은 단방향** — 로드맵 진행률 → 스탯. 스탯끼리 의존 금지.
   이유: 순환 참조 + 규칙이 복잡하면 사용자가 규칙을 최적화하기 시작함(Oblivion 실패 사례).
2. **가중치는 0/1** — 기여하냐 안 하냐만. 소수점 금지(근거 못 댐 + 전부 조금씩 기여하면 스탯이 평평해짐).
   한 로드맵은 되도록 한 스킬에만. 무매핑 로드맵 허용(`meta/learning`).
3. **분모는 기여 로드맵 항목 합산** — 스킬 % = 완료 합 / 전체 합.
   예: 설득 60·말하기 40이면 설득만 100% 해도 Rhetoric 60% → 선행조건이 필요 없음.
4. **참조(ref)는 진행도 무관** — `이 로드맵 밖`은 길잡이 링크. 체크해야만 오름.
   (참조 1144개·상호참조 152쌍, 전부 탐색용)
   **`위임`은 여기서 빠졌다 (2026-08-27) — 참조가 아니라 분모다. 규칙 8.**
5. **헤딩 `택 1` 그룹 = 분모 1** — 안에서 가장 높은 lv 하나로 대표(lv:4 있으면 done, lv:3이면 theory), doing은 하나라도 있으면 전파. 초과 학습은 %에 안 더함(로드맵 요구는 1개, 나머지는 로그에 남음). 인라인 8개는 자기완결형이라 일반 항목. 계산은 `build_stats.py`.
6. **manipulation·propaganda도 Rhetoric** — 스탯은 능력 측정이지 인성 아님. 뭘 배웠는지는 로드맵 화면에 보임.
7. **이론/실습은 한 항목의 `lv`(수준 4단계) + `doing`(진행중 플래그) 두 필드** (2026-08-29 개정 —
   구 단일 `s` 사다리는 "이론완료 후 구현 진행중"을 표현 못 해 구현을 시작하면 학습%가 내려갔고,
   "이름만 앎"과 "안 함"이 구분 안 됐다. 그 전의 별개 파일 방식은 2026-08-25에 폐기).
   실전 없이 안 느는 축도 파일은 하나, 대신 수준으로 가름:
   **기록없음 안함 / lv:1 이름만 앎 / lv:2 개념(한 문장 설명) / lv:3 이론(이해·대화 실증) / lv:4 완료(실전 실증)**.
   `doing:true`는 어느 lv에서든 붙는 진행중 표시 — 수준과 직교.
   이론 진도는 lv:3까지 막히지 않고 계속 나감 — 실증이 안 돼도 학습은 진행됨.
   **퍼센트는 하나 — 숙련도뿐이다** (2026-09-01 확정).
   - **숙련도% = Σ WEIGHTS[lv] / 분모.** lv:1·2도 가중치만큼 센다.
     `WEIGHTS = {1: 0.05, 2: 0.2, 3: 0.6, 4: 1.0}` (원본은 `tools/build_stats.py`,
     `stats.json`의 `weights`로 프론트에 실려 간다). 이름만 스무 개가 개념 하나,
     3→4 간격이 제일 크게 — 실증이 목표로 남게 볼록한 곡선
   - **카드 색칠 폭 = 그 가중치.** 색 길이와 숫자가 같은 값을 본다(lv/4 등간격에서 전환)
   - `stats.json`·화면의 `percent`가 이 숙련도다. **`learn_percent`·`mastery_percent`는 없다**
   - 폐기: 옛 **실증%(lv:4/분모)·학습%((lv:3+4)/분모)** 두 개. 칸의 수준은 카드가 lv 색으로
     이미 보여주므로 퍼센트를 쪼갤 이유가 없었다. lv:4·lv:3 **개수**는 `done`·`theory`로 그대로 남아
     위임 상태 파생(규칙 8)과 화면의 "구현 n / 이론 n"에 쓰인다
   판정 시 실증(lv:4) 경로 3종:
   - **현장형**(운동·대면 대화): 사용자 후기 자기신고 → 로그, `ev`에 후기 요약
   - **산출물형**(코드·그림·사운드·글): `works/<로드맵 경로>/`의 파일
   - **채팅형**: Claude와의 채팅 실습. **텍스트·메시지 항목에만** — 음성·대면 항목은 채팅으로 못 채움.
     대면·음성 스킬(speaking 등)은 채팅으로 lv:4 금지, lv:3까지만
   실패·상세 기록 (2026-08-26 확정):
   - **실패한 시도도 로그 한 줄** — `lv`·`doing:true` 유지 + `ev`에 전말. 성패는 로그의 `lv`·`ev`가 담당,
     결과 전용 파일 금지(이중 기록). 형식은 `docs/progress-format.md`
   - 관찰·복기 등 **긴 기록물은 `works/<로드맵 경로>/`에 md**로 두고 로그 `ev`에 경로 참조.
     한 줄 로그가 목차, 파일이 본문. 타인 정보가 들어가는 파일은 repo 비공개 확인 후 작성
8. **`위임` 칸 = 분모 1, 상태는 대상 로드맵에서 파생** (2026-08-27).
   위임은 **중요해서 파일로 뺀 필수 부품**이지 선택 사항이 아니다. 분모에서 빼두면
   "leverage 21항목을 다 끝냈는데 coercer가 0%"라는 구멍이 난다. 그래서:
   - **불릿 하나 = 분모 1칸.** 581개(2026-08-30 기준 — `택 1`의 로드맵 옵션 285개를 체크박스에서
     전환. 그룹 안에 든 289개는 그룹에 흡수돼 분모 가산은 그룹 밖 292칸 그대로, 분모 불변 검증 완료).
     같은 대상을 두 불릿이 가리키면 두 칸이다 — 로드맵이 두 단계에서 요구한 것이므로
     (aspnet-core §1의 `Git`·`GitHub, GitLab, BitBucket`이 둘 다 `git-github`)
   - **택 1 안 위임 옵션의 "주력" 선택은 `pick` 레코드** (2026-08-30, 화면 전용) — 집계 무관이고,
     "위임 칸엔 로그 금지"의 **유일한 예외**다(진행도가 아니라 선택 표식이라서).
     상세는 `docs/progress-format.md`
   - **상태는 대상 로드맵의 *자기 항목* 집계에서 파생한다.**
     전부 lv:4 → 1(완료) · 전부 lv:3 이상 → 2(이론완료) · 기록 하나라도(lv:1·2 포함) → 3(**부분 진행**) · 없으면 미기록.
     **진행중(doing)은 상태와 별개** (2026-08-29 분리) — 대상에 `doing:true` 레코드가 실제로 있을 때만
     위임 칸에 doing이 얹힌다. 상태 3을 통째로 진행중으로 세던 옛 규칙은 위임 대상이 조금이라도
     진행되면 상위 로드맵마다 진행중 배지가 박히는 오탐을 냈다(ai-engineer 사례).
     stats.json엔 `delegate_state`(1/2/3) + `delegate_doing`(bool) + `delegate_mastery`(%) 세 필드로 나간다.
     **숙련도는 lv 환산(1→4·2→3·3→없음)을 쓰지 않고 대상의 `delegate_mastery`를 그대로 받는다**
     (2026-09-01) — 상태 3(부분 진행)이 lv 없음이라 0으로 떨어지던 구멍을 메운다.
     `delegate_mastery`는 **자기 항목만 센 1패스 값**이라 대상 자신의 `mastery_percent`(2패스)와
     다르다 — 위임 칸은 `delegate_state`와 같은 이유로 1패스를 써야 한다(아래 재귀 금지).
     프론트도 같은 필드를 읽는다: 자체 환산표(완주 100 / 이론 75 / 학습%×0.75)는 폐기됐다
     위임 칸엔 **로그를 쓰지 않는다** — 원천은 대상 로드맵의 로그다
   - **재귀 금지, 2패스 고정.** 대상의 위임 칸은 보지 않는다. social skill끼리 순환 참조가
     가능해서(A가 B를, B가 A를) 재귀로 파생시키면 무한루프가 난다.
     그래서 대상이 100%를 못 채워도(자기 위임 칸이 남아서) 위임 칸은 완료로 잡힌다 —
     의도된 것이다. 부품을 다 배운 사람에게 부품의 부품까지 요구하지 않는다
   - 계산은 `tools/build_stats.py`(`deleg_state`), 화면은 `front/js/merge.js`가
     **stats.json의 `delegate_state`를 읽기만** 한다. 두 군데서 계산하면 분모가 조용히 어긋난다

## 수치

- 스킬 % = 완료 항목 / 매핑된 로드맵의 항목 합. 계산은 `tools/build_stats.py`, 결과는 `data/stats.json`(생성물, 손대지 말 것)
- 집계 키는 `(sec, item)` — 로그와 같은 키. 한 섹션에 같은 이름이 두 번 나오면 로그로 구분이 안 되므로 분모에서도 한 번만 셈. 분모 합계 숫자는 여기 안 씀 — 원본은 `data/stats.json`(재실행마다 갱신)
- PHYSIQUE는 % 아님 — 외부 표준표 백분위. 자체 임계값 발명 금지. 표준표·입력 경로는 아래 "PHYSIQUE" 절
- CHARACTER는 행동 로그 — **재료(뭘 셀지) 보류**(2026-08-26). 입력 경로는 생기면 PHYSIQUE와 동일(채팅 자기신고→jsonl)
- INVENTORY는 수치 없음 (목록)
- `stats.json`에는 축 트리와 별개로 **`roadmaps` 평면 인덱스**가 같이 나온다 —
  `{"<분야>/<경로>": {total, done, theory, doing, delegate_state, delegate_doing, delegate_mastery,
  percent, learn_percent, mastery_percent}}` 348개 전부. 최상위엔 `weights`(숙련도 눈금)도 같이 나간다.
  `delegate_state`는 **이 로드맵을 위임한 칸이 갖는 상태**(규칙 8) — 프론트가 그대로 읽는다.
  축 매핑과 무관하므로 **UNMAPPED(health·meta/learning)도 여기엔 들어감**.
  프론트가 로드맵 카드·기술 습득치를 그릴 때 쓰는 유일한 분모 원천
  (`roadmaps/<분야>/index.json`의 `items`는 택 1 접기 전 원시값이라 진행률에 쓰면 안 됨)

**분야→축 요약표 금지** — 원본은 `AXES` 하나. 요약표는 만들자마자 어긋났음(health→PHYSIQUE 등).

## PHYSIQUE (2026-08-26 확정 — 구 미정 항목)

- **구조는 다른 축과 동형** (2026-08-26 사용자 확인): 다른 축이 "체크 → 스킬 % → 축"이듯
  PHYSIQUE는 "**실측 → 스킬 백분위(=숙련도) → 축**". 기록이 오르면(3대 200→300, 쿠퍼 거리↑)
  해당 스킬 백분위가 오르고 축에 반영됨. 스킬 5개는 `AXES` 선언(Strength·Endurance·Stamina·Mobility·Recovery)
- **종목 → 스킬 귀속** (physique.jsonl의 `kind` 기준):
  squat·bench·deadlift → Strength / cooper → Endurance / pushup·plank → Stamina /
  sit-and-reach → Mobility. 새 종목 측정 시작 시 여기에 귀속 추가.
  축 게이지 = 실측 있는 스킬의 백분위 집계(방식은 구현 때 확정)
- **표준표** (자체 임계값 발명 금지 원칙의 실체):
  - 근력: **Strength Level**(strengthlevel.com) 체중·나이 보정 백분위 — 스쿼트·벤치·데드리프트.
    현재 헬스장 미등록이지만 표는 자(尺)라 선정해 둠. 데이터는 측정 시작 시 유입
  - 유산소: **쿠퍼 테스트**(12분 달리기) → VO2max 추정 → **ACSM 연령대 백분위**
  - 근지구력(pushup)·유연성(sit-and-reach): **ACSM 노름** — 장비 없이 측정 가능
  - Recovery(수면시간·HRV): 표준표 미선정 — 보류. 신체조성(체지방률)도 측정 수단(인바디) 생기면 추가
  - 저장·표시는 라벨(Beginner~Elite)이 아닌 **백분위 숫자** — 다른 축 %와 같은 스킨
- **입력 경로**: 채팅 자기신고("12분에 2.4km") → Claude가 **`data/log/physique.jsonl`**에 한 줄 append.
  로드맵 로그와 같은 append-only·같은 경로(로그), 차이는 로드맵 키가 없는 것뿐 —
  "결과·실측은 전부 로그" 한 규칙(social 결과는 로그인데 실측만 딴 데 두면 모순이라 로그로 통일).
  기록이 나빠져도 그대로 적음. **파일은 첫 실측 때 생성** — 빈 틀 미리 안 만듦.
  `build_stats.py` 환산 로직(종목별 최신값→백분위)도 첫 데이터 유입 시 구현(추측성 코드 금지)

## INVENTORY

- 목록 패널. 랭크·% 없음 — 자격증·경력엔 진행률 개념이 없고, 재정 숫자(생존 개월 등)는 그 자체로 읽힘
- 로드맵 기여 없음 — 체크박스는 공부, 인벤토리는 결과(합격해야 아이템)
- 저장: `data/inventory.json`, 월 1회 수기. 값 넣기 전 repo 비공개 또는 `.gitignore`
- 항목 형식 — 날짜는 `YYYY-MM` 또는 `YYYY-MM-DD`
  - `degrees` `{school, major, level, at}` — 만료 없음
  - `certifications` `{id, name, issuer, at, expires?, score?}` — 면허·어학 성적도 여기. 점수·만료는 있는 것만.
    **`id`는 `certifications/<분야>.md`의 id를 그대로 씀**(2026-08-26) — 이름 문자열로 대조하면 표기가 흔들려
    "딸 수 있는 것"과 "딴 것"이 안 붙는다. 목록에 없는 자격이면 id를 새로 지어 넣되 자격증 파일에도 추가할 것
  - `works` `{name, path, at}` · `career` `{org, title, from, to}`
- 재정 배제: Income(저축률에 중복), 투자수익률(소음+최적화 유도), 부채(순자산에 반영), 신용점수(행동 여지 없음)

## 매핑 안 된 로드맵

`build_stats.py`의 `UNMAPPED`. 사유:

- `health/` — 운동법 공부 ≠ 몸. PHYSIQUE는 실측 전용
- `meta/learning` — 의도적 무매핑 (2026-08-26 작성 후에도 유지). 학습법은 **다른 분야 진행 속도로 이미 드러남** —
  별도 축을 주면 같은 실력을 두 번 세는 꼴. 구 REASON 축 폐기 때의 판정을 그대로 승계.
  나머지 둘은 매핑됨: `meta/time-management` → CHARACTER.Temporal, `meta/habits` → CHARACTER.Volition(스트릭 재료는
  `habits/tracking-recovery`의 30·90일 항목)

  고아 로드맵: math→KNOWLEDGE.Formal, CS-Theory→Technical, Data-DB→Engineering, meta/learning→무매핑.
  맥 세션 "Gf/Gc 섞기 싫다"와 모순 아님 — 측정 불가한 쪽을 지운 것도 분리임
- **Bloom 랭크 라벨** — 깊이 척도를 넓이 재료에 씌운 것
- **랭크 0~5** — 표시 스킨이라 매핑 데이터에 둘 게 아니고, 임계값도 근거가 없었음. 값은 %로 저장·표시
